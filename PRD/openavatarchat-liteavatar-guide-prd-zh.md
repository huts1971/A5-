# A5 `/guide` 页 OpenAvatarChat LiteAvatar 集成 PRD

生成时间：2026-06-28

## Problem Statement

当前 A5 景区 AI 数字人导览系统在 `/guide` 页面已经具备稳定的 AI 导游问答、来源卡展示、流式返回和后端 TTS 能力，但数字人展示仍基于旧的 Live2D Haru 轻量形态。现状存在几个直接问题：

- 数字人表现与语音播报是两套相对松耦合的系统，难以形成更完整的“在和导游对话”的游客体感。
- 现有 `/guide` 数字人主要依赖前端状态驱动，无法直接复用成熟的语音驱动数字人链路。
- 现有语音输入能力主要是浏览器侧方案，稳定性和可控性有限。
- 游客端希望在不破坏当前 A5 问答真相源、来源可追溯和低延迟体验的前提下，引入更完整的数字人听说体验。

本需求的核心不是替换 A5 的 AI 导游问答真相源，而是在 `/guide` 页面中，用 `OpenAvatarChat` 的 `TTS + LiteAvatar` 替换旧数字人播放链路，并补充麦克风对话能力，同时继续保留 A5 现有的结构化优先、来源可追溯、流式问答链路。

## Solution

游客在 `/guide` 页面中继续使用 A5 原有的文字问答、来源卡和流式回答能力，但左侧数字人区域替换为基于 `OpenAvatarChat` LiteAvatar 的本地数字人视频播报面板。A5 继续负责 AI 导游问答的答案生成与来源展示；独立的 avatar service 负责：

- 麦克风输入识别为文本
- 接收 A5 的流式回答文本
- 使用 `OpenAvatarChat` 的 TTS 做流式语音合成
- 使用 `LiteAvatar` 生成数字人音视频并在左侧区域实时播报

最终游客在 `/guide` 页面获得的体验是：

- 右侧仍然是 A5 原有的 AI 导游问答与来源卡
- 左侧是新的 LiteAvatar 数字人视频区域
- 文字输入和麦克风输入都可用
- 问答仍然由 A5 真相源输出
- 数字人播报自动触发、可被新问题打断
- avatar service 失败时，问答与来源卡仍正常，不回退旧 Live2D

## User Stories

1. 作为游客，我希望 `/guide` 页面继续保留现有的 AI 导游问答入口，这样我不用重新学习新的使用方式。
2. 作为游客，我希望数字人能够直接播报 AI 导游回答，这样我会感觉自己是在和导游交流，而不是只是在看文本。
3. 作为游客，我希望文字输入提问后，右侧回答和左侧数字人播报都能尽快开始，这样等待感不会过重。
4. 作为游客，我希望数字人的播报不阻塞文字回答和来源卡展示，这样我能先看答案再听讲解。
5. 作为游客，我希望新问题可以立即打断上一段播报，这样对话节奏更自然。
6. 作为游客，我希望保留当前 A5 的来源卡展示，这样我能知道答案依据来自哪些景区资料或实时来源。
7. 作为游客，我希望文字输入和语音输入都能使用，这样我可以根据场景选择更方便的交互方式。
8. 作为游客，我希望点击麦克风开始说话、点击结束即可自动提问，这样语音交互足够直接。
9. 作为游客，我希望语音识别成功后，识别文本也像普通用户消息一样显示在聊天区，这样对话记录统一且可复看。
10. 作为游客，我希望语音识别失败时系统只给轻提示，不要发出空问题或错误问题，这样不会打乱我的会话。
11. 作为游客，我希望左侧数字人区域始终有非常短的中文状态提示，这样我知道它当前是在准备、聆听、识别、思考还是播报。
12. 作为游客，我希望左侧状态提示简洁，不要堆很多技术信息，这样页面不会显得复杂。
13. 作为游客，我希望在进入 `/guide` 时就能看到页面可用，即使数字人服务还在准备中，这样不会因为数字人慢启动而无法提问。
14. 作为游客，我希望当数字人服务尚未准备好时，文字问答依然能继续，这样不会错失提问机会。
15. 作为游客，我希望数字人服务断开后，文字问答仍然可用，这样不会因为数字人故障导致整个 AI 导游不可用。
16. 作为游客，我希望数字人断开后系统能自动尝试恢复连接，这样不用每次都手动刷新页面。
17. 作为游客，我希望连接恢复后后续新问题还能继续播报，这样体验能自我恢复。
18. 作为游客，我希望历史回答默认不再提供单独播放按钮，这样主界面更简洁。
19. 作为游客，我希望欢迎语仍以文字呈现，但不自动播放一段欢迎音频，这样不会刚进入页面就被语音打断。
20. 作为游客，我希望文字提问和语音提问使用同一套数字人状态机，这样整个 `/guide` 页面体验统一。
21. 作为游客，我希望右侧聊天区布局不要被大幅重构，这样现有的问答体验和阅读节奏能保留。
22. 作为产品负责人，我希望继续保留 A5 原有的 AI 导游问答真相源，这样景区知识检索、来源筛选和业务边界不会被外部项目接管。
23. 作为产品负责人，我希望新数字人只接入 `/guide` 页面，这样本轮改动范围聚焦且风险可控。
24. 作为产品负责人，我希望首版数字人先使用 LiteAvatar 默认人物，这样先把链路跑通，再考虑定制景区导游形象。
25. 作为产品负责人，我希望本轮边界明确为本地单机演示版，这样目标集中在稳定演示，而不是外网部署。
26. 作为产品负责人，我希望 avatar service 独立运行，这样不会把 A5 backend 的业务 API 和重型数字人依赖混在一起。
27. 作为产品负责人，我希望 A5 backend 保持现状，不被 OpenAvatarChat 的依赖栈拖入风险，这样现有演示功能更安全。
28. 作为产品负责人，我希望最终提供 Windows 本地一键联合启动脚本，这样现场演示和交接更顺畅。
29. 作为前端开发者，我希望前端继续使用现有 `/api/chat/stream`，并把流式文本双路消费给聊天区和数字人服务，这样可以在不改问答真相源的前提下尽量保住低延迟。
30. 作为前端开发者，我希望 avatar service 提供 A5 专用桥接接口，这样前端不用直接理解 OpenAvatarChat 原始协议。
31. 作为前端开发者，我希望数字人视频区域可以按美观做适配调整，但不打破 `/guide` 的整体结构，这样集成成本更低。
32. 作为后端开发者，我希望 A5 backend 仍只负责问答与来源卡，不承担音视频转发代理，这样职责清晰且延迟更低。
33. 作为后端开发者，我希望 avatar service 通过独立桥接层承担会话、录音、打断和状态同步，这样两个系统边界稳定。
34. 作为测试人员，我希望文字输入路径和语音输入路径都能独立验收，这样回归测试更明确。
35. 作为测试人员，我希望 avatar service 挂掉时仍能完整验证 A5 问答与来源卡，这样故障场景可控。
36. 作为维护者，我希望本地运行说明写清楚模型下载、初始化、常见故障和联合启动方法，这样后续接手成本更低。

## Implementation Decisions

- `/guide` 页面继续作为唯一的数字人接入页面，首页和其它页面不纳入本轮替换范围。
- A5 现有 AI 导游问答链路保持不变，答案生成仍由 A5 的结构化优先与来源可追溯链路负责。
- 数字人服务改为独立 avatar service，不并入现有 A5 backend 进程。
- avatar service 复用 `OpenAvatarChat`，但只做必要的接口适配与桥接，不做 LiteAvatar 或 TTS 算法级修改。
- avatar service 使用独立虚拟环境，与 A5 backend 环境隔离。
- 前端直连 avatar service，不让 A5 backend 充当音视频代理层。
- 前端成为本次集成中的编排中心之一：
  - 负责用户文字输入和麦克风录音触发
  - 负责消费 A5 `/api/chat/stream`
  - 负责把流式回答同步转发给 avatar bridge
  - 负责驱动左侧状态提示和右侧聊天展示
- A5 专用 avatar bridge 负责完整编排职责：
  - 创建与销毁 avatar session
  - 开始录音与结束录音
  - ASR 文本回传
  - 文本播报触发
  - 流式回答增量转发
  - 打断控制
  - 状态同步
  - 健康检查
- 一个 `/guide` 页面生命周期只维护一个 avatar session；进入页面初始化，离开或刷新页面销毁。
- 若 avatar session 尚未 ready，A5 问答仍照常进行；这类回答不做排队补播，后续新问题在 session ready 后进入播报。
- 文字输入与语音输入共享统一状态机：
  - 未连接
  - 准备中
  - 正在聆听
  - 识别中
  - 思考中
  - 播报中
- 语音输入交互采用半双工模式：点击开始说话、点击结束；识别完成后自动发问。
- 识别成功后的文本必须进入聊天记录，作为普通用户消息保留。
- 新问题到来时必须立即打断当前数字人口播，不恢复旧问题的历史播报。
- 右侧历史回答不再保留旧的播放按钮或重新播报能力。
- 当前旧数字人主链路在 `/guide` 页面中移除；但如果其它页面仍使用全局资源，则不在本轮做全站误删。
- 欢迎语文字保留，但不自动触发新数字人欢迎播报。
- 首版数字人形象使用 LiteAvatar 默认人物，不纳入景区导游形象定制。
- 本轮边界锁定为 Windows 本地开发测试与单机演示，不承诺公网部署、手机访问、TURN、外网穿透等能力。
- 项目内新增独立的 avatar service 集成目录，采用轻量适配层管理，不把 OpenAvatarChat 业务性修改散落到 A5 backend 中。
- 输出物包含一键联合启动脚本，服务于 Windows 本地演示。

## Testing Decisions

- 好的测试应只验证外部行为，不绑定内部实现细节。重点验证游客在 `/guide` 页面中能否完整完成提问、接收回答、查看来源、听到数字人口播，以及在异常时是否仍可继续文字问答。
- 优先测试以下模块与行为：
  - A5 `/api/chat/stream` 在新前端编排下仍能稳定返回流式文本与来源卡
  - `/guide` 页面在文字输入场景下能触发 LiteAvatar 自动播报
  - `/guide` 页面在麦克风输入场景下能完成录音、识别、自动发问和自动播报
  - 新问题对当前播报的打断行为
  - avatar service 不可用时的降级行为
  - session 未 ready 或中途断线时的状态与恢复行为
- 前端验证优先沿用项目现有 visitor 验证思路，尤其关注：
  - `npm run build`
  - `/guide` 手动流式问答链路
  - 来源卡仍然出现
  - 页面无遮挡、无白屏、无水平溢出
- 后端与服务侧验证优先采用行为级测试和手动联调验证，不要求对 LiteAvatar 算法内部做单元级覆盖。
- 对 adapter/bridge 模块的测试重点应放在：
  - 会话生命周期
  - 录音开始/结束编排
  - 流式文本转发
  - 打断控制
  - 状态同步
- 对异常路径的测试重点应放在：
  - ASR 返回空文本
  - avatar service 未连接
  - 播报过程断线
  - A5 问答正常而数字人口播缺失时页面是否仍可继续演示

## Out of Scope

- 替换 A5 现有 AI 导游问答真相源
- 将 OpenAvatarChat 默认 LLM 直接接管景区问答内容生成
- 改造 A5 的结构化优先、来源可追溯、联网补充、日志等业务能力
- 公网部署、TURN、外网穿透、移动端跨设备联调
- 多用户并发与多 session 高压验证
- LiteAvatar 人物素材定制与景区品牌形象统一
- 逐字字幕同步、高亮追踪、历史回答回放
- 首页或其它页面的数字人展示替换
- OpenAvatarChat / LiteAvatar 算法级优化与模型效果调优
- 管理后台可视化配置页

## Further Notes

- `OpenAvatarChat` demo 的低延迟体验建立在更短、更直接的默认回答链路之上；A5 集成后如需尽量保持游客端低延迟，必须走流式播报方案，而不是等待完整 answer 再启动数字人。
- 首版不锁定新的口播文风；A5 现有回答风格先保留，后续再做更有人情味的游客端风格优化。
- 本轮工程目标以“打通本地可稳定演示的完整链路”为先，而不是追求最优的数字人美术或公网部署能力。
